# App reliability and security audit - 2026-10-23

**Follow-up:** App-side fixes have since been implemented. See
[the fix status and remaining native limitations](app-audit-fixes-2026-10-23.md).
The findings and reproduction results below describe the pre-fix audit snapshot.

Scope: TibaneApp working tree, app 0.1.13+79, official LibWallet 0.5.5.
This is a local engineering audit, not a production security certification.
No production code was changed by this audit. Only audit tests and this report
were added/extended. Existing unrelated working-tree changes were preserved.

## Executive Summary

The Solana recovery-phrase import failure is NOT the only outstanding problem.
There are release-blocking issues in backup/restore, Ethereum signing and SEND,
and the browser's trust boundary. Several additional defects can cause stale
transaction state, misleading success messages, or operations with no feedback.

No theft, private-key exfiltration, or loss of real funds was demonstrated.
No real wallet secrets, simulator databases or clipboard content were accessed.
There were no broadcasts, real 2FA requests, app restarts or simulator restarts.

Evidence labels:
- Reproduced: executed locally with fixtures, fake transports or temporary native
  databases. This does not imply a live end-to-end transaction was exercised.
- Static-confirmed: the current implementation directly contains the defect;
  the affected real-device ceremony was not executed.
- Conditional risk: an identified failure path whose complete operational
  consequence still needs a dedicated integration test.

P1: fix before a release involving the affected feature. P2: important reliability
or transaction-understanding defect. No P0 was established in this audit.

## P1 Findings

### A01. Browser requests are not bound to the actual frame/document

Owner: app. Evidence: static-confirmed; benign callback injection reproduced in
an offline JavaScript VM, not a mobile exploitation test.

`lib/screens/browser/dapp_browser_view.dart:163` takes the security origin from
`_currentUrl`, not the sender of the bridge message. The installed WKWebView
plugin injects the JavaScript channel into every frame
(`webview_flutter_wkwebview/.../webkit_webview_controller.dart:497`,
`isForMainFrameOnly: false`). Consequently, an iframe can send a request that
the app attributes to the top-level site. After awaiting the native request,
the app checks only `mounted`, not whether the document/origin has changed.

Additionally, line 196 interpolates the unvalidated `req['id']` directly into
`__libwalletResolve($id, ...)`. An expression in this field executes as JavaScript
when the response is delivered. The offline proof set only a harmless boolean.
Combined with iframe access, this is a cross-frame trust-boundary issue, not
merely a page executing JavaScript on itself. Signing still has approval gates;
automatic signing/fund theft was not demonstrated.

Action: main-frame/origin-aware native messaging, strict request schema and
JSON-encoded IDs, document-generation binding, and event delivery scoped to
the authorized origin. Test with a cross-origin iframe and navigation in flight.

### A02. Backup restore rejects valid non-Solana and already-present wallets

Owner: app. Evidence: static-confirmed.

`lib/services/wallet/libwallet_backend.dart:2812` restores the bundle, then accepts
only a newly appearing `ed25519` wallet. An Ethereum-only backup fails with
`Backup contains no Solana (ed25519) wallet`; importing a wallet already in the
database also fails because its ID is in `before`.

Validation happens after database mutation. The catch block at line 2900 removes
only the selected Solana wallet, not other technical wallets restored by the
same bundle. Failed password checks can therefore leave a partial import.
No destructive overwrite of an existing real wallet was attempted or proven.

Action: validate in an isolated store, handle all supported curves and duplicate
IDs explicitly, and commit/roll back the complete bundle atomically.

### A03. Ethereum MPC signing requires all shares, while the app collects two

Owner: LibWallet native/app contract. Evidence: reproduced against native 0.5.5.

`test/app_audit_signing_integration_test.dart` creates fresh, offline 3-participant
wallets. Both have threshold 1. Solana signs with two local shares. Ethereum
fails with two: `DKLs signing requires all shares to be unlocked`; it succeeds
with all three. This also occurs for a mnemonic-migrated Ethereum fixture.

The app's `lib/services/wallet/signing.dart:19` uses threshold + 1 and its sign
sheet disables RemoteKey collection. The production 2-local + RemoteKey
committee therefore does not satisfy the tested EVM native requirement.
This was reproduced with signMessage, not a funded EVM send.

Action for Mark: support the advertised signing subset or expose the true
algorithm requirement. Do not change the app to request an unavailable recovery
share on every payment without reviewing the intended security design.

### A04. Ethereum SEND preflight is not simulating the intended transaction

Owner: app/native adapter contract. Evidence: two strict tests reproduced.

`lib/services/wallet/libwallet_backend.dart:2920` passes a generic transfer with
an account ID as `from`, `amount` and `asset`. Native EVM simulation forwards
the account ID to `eth_call`, omits native `value`, and does not build ERC-20
transfer calldata. For ERC-20, the RPC call targets the recipient rather than
the token contract. The low-level address/value control works.

`test/multichain_transfer_audit_test.dart` captures these calls on loopback RPC.
They are invalid for real EVM nodes or simulate something different from the
intended spend. The permissive test RPC returning success does not validate them.
SEND requires this preflight before authorization, making this a flow blocker.

Action: build/normalize the actual chain-specific transaction before simulation
and use the same built transaction for review and submission.

### A05. Solana seed-to-MPC import is unsupported by the shipped native path

Owner: LibWallet native capability/SDK documentation. Evidence: native fixture
reproduced in `test/mnemonic_promotion_integration_test.dart`.

The app now calls `promoteMnemonic`, not raw-key `promote`. Native 0.5.5 still
rejects ed25519 with `curve ed25519 not yet supported`. EVM migration preserves
the first Ethereum address in the isolated control. This does not prove that
all derived accounts/chains or production RemoteKey ceremonies migrate.

Action for Mark: implement and test address-preserving ed25519 mnemonic
migration, or report unsupported capability before onboarding/2FA begins.

### A06. Password change does not support the app's password-only MPC wallets

Owner: app. Evidence: static-confirmed.

`lib/services/wallet/creation.dart:21` intentionally creates the no-biometrics
committee `[Password, Password, RemoteKey]`. But `changePassword` at
`lib/services/wallet/libwallet_backend.dart:1171` requires StoreKey metadata,
and its remaining implementation also requires an old StoreKey participant.
These legitimate wallets cannot use that management operation.

Action: implement the correct management committee per wallet model, and gate
unsupported actions before sending a 2FA code. Include raw imports, D5 and
biometric-created wallets in management tests.

### A07. Password rotation can split the credentials of one logical wallet

Owner: app. Evidence: conditional risk from confirmed control flow.

`changePassword` reshares only `_walletId` (backend line 1253). The user-facing
wallet can include both ed25519 and secp256k1 technical wallets, while the export
screen selects both and `exportBackupJson` line 2750 verifies all targets using
one password. If password rotation succeeds for only one sibling, neither the
old nor new password can export the complete group through this flow.

The actual remote reshare was not performed, so this is not claimed as a
reproduced user lockout. The single-wallet implementation is confirmed.

Action: define group-wide rotation/recovery with partial-failure handling, or
expose and support separate credentials explicitly. Test export after rotation.

### A08. Automatic backup covers one technical wallet and overwrites one file

Owner: app. Evidence: static-confirmed.

`lib/services/wallet/libwallet_backend.dart:2665` calls
`exportBackupJson(password)` without the logical group's wallet IDs. The default
exports only `_walletId`. It then writes the single global
`tibane_wallet_autobackup.json`. Backing up another wallet replaces the previous
copy; a Solana-active multi-curve wallet also omits its Ethereum/Bitcoin sibling.
Manual export's group selector does not repair this separate automatic path.

Action: per-logical-wallet backup manifests, complete eligible group coverage,
atomic file replacement and an explicit UI inventory of what is protected.
Do not describe a local file write as proof of a completed cloud upload.

### A09. Wallet grouping uses name/time rather than a persistent relationship

Owner: app. Evidence: grouping reproduced; destructive consequence static.

`lib/services/wallet/logical_wallet.dart:129` groups opposite-curve wallets with
the same name and creation times within ten minutes, without proving that they
belong to one creation operation. The new audit fixture shows two independently
identified wallets merging into one group without a parent/group relationship.
Group remove at `lib/screens/wallet/wallets_management_screen.dart:324` removes
every ID in that group. It can therefore include an unrelated wallet. Export
and rename are also group-wide. No real wallet was deleted in this audit.

Action: persist an explicit logical group ID at creation/import; use the heuristic
only for user-confirmed legacy migration, never as a destructive boundary.

## P2 Findings

### A10. Switching accounts retains an actionable swap quote from the old account

Owner: app. Evidence: widget reproduction.

`lib/screens/swap_screen.dart:209` reacts to connect/disconnect and network
changes, but not a connected-to-connected account switch on the same network.
The fixture confirms that the old quote remains and the Swap button stays
enabled after the public key changes. Holdings loads also lack account-generation
checks after awaits. This can show the wrong balance/quote and fail execution;
incorrect spending or theft was not demonstrated.

Action: bind holdings, quote, review and execution to one immutable
account/network context; invalidate them and cancel stale results on changes.

### A11. SEND converts exact user amounts through floating point

Owner: app. Evidence: widget reproduction.

`lib/screens/wallet/send_screen.dart:729` parses a double, multiplies it by a
double scale, then rounds into BigInt. Entering `0.123456789012345678` with 18
decimals produces base units different from `123456789012345678` before
simulation. Similar floating-point conversions exist in staking/burn paths.

Action: use the existing exact decimal/BigInt parser throughout financial input;
reject unsupported precision instead of silently rounding it.

### A12. Non-finite amount input raises an uncaught SEND exception

Owner: app. Evidence: widget exception reproduced and deterministic numeric
characterization retained in `test/send_form_test.dart`.

Pasting `NaN` passes the null/<=0 checks, then line 735 throws
`Unsupported operation: Infinity or NaN toInt` before the try/catch. The widget
test execution captured that stack. This establishes an uncaught operation,
not that every release platform necessarily terminates the entire process.

Action: exact finite amount validation, bounded input and graceful validation
errors; cover NaN, Infinity, exponent notation, huge values and excess decimals.

### A13. Bitcoin-family SEND MAX discards the quoted spend plan

Owner: app. Evidence: static-confirmed, backed by SDK contract and earlier
loopback-native checks; no broadcast.

`lib/screens/wallet/send_screen.dart:686` saves only `result.max` as text.
The SDK's `MaxSendableResult` explicitly requires carrying `bitcoinUtxos` and
`bitcoinFeeRate` into the eventual UnsignedTransaction to reproduce a sweep.
The app does not pass either through `sendWithKeys`. Replanning fees/inputs can
make MAX exceed spendable funds or invalidate the preview.

Action: retain a context-bound spend plan, pass it to simulation/signing, and
invalidate it on recipient, amount, account, UTXO or network changes.

### A14. Browser transaction approvals use the wrong encoding and blind previews

Owner: app. Evidence: wrong preview reproduced; omitted structured details static.

`lib/services/wallet/libwallet_request_bridge.dart:103` decodes every raw payload
as base64, although the SDK specifies hex for EVM/Bitcoin. A hex fixture renders
unrelated bytes. Some input shapes can also throw before the approval catch.
The pending-request subscription does not handle the returned Future's errors.

The generic `showSignSheet` in `lib/screens/browser/approval_sheets.dart:34`
shows an account and raw bytes, not the SDK's transaction effects, recipient,
amount, approvals, fees or warnings. Users cannot reliably understand the spend.
This is security-relevant even when the transaction can technically be signed.

Action: chain-aware decoding, structured effects/warnings, requested-account
binding and a guaranteed approve/reject/error outcome for every request.

### A15. Batch signing failures can produce no user feedback

Owner: app. Evidence: static-confirmed.

`lib/services/wallet/libwallet_backend.dart:3061` and 3088 catch individual signing
errors and return null entries without setting backend error state or throwing.
`lib/screens/staking/staking_detail_screen.dart:632` reports a failure only when
`wallet.error` is set. A null signature with no previous error can therefore
finish silently. Shared signing helpers affect more than staking.

Action: structured per-transaction errors and explicit partial-success/failure
UI. Never offer an unqualified retry of an already broadcast batch.

### A16. SEND/staking say success or confirmed at broadcast time

Owner: app. Evidence: static-confirmed.

`lib/screens/wallet/send_screen.dart:790` shows the success screen after the send
returns a transaction/hash. The balance store's confirmation refresh runs in
the background; the success screen is not gated on a confirmed chain result.
Staking similarly labels a non-null signature as confirmed (line 626). A hash
means submission, not final execution. Swap has a separate confirmation path.

Action: Submitted/Pending first, then confirmed/failed/expired based on chain
status, with Activity remaining authoritative across app restarts.

### A17. Activity is not fully network-scoped and Bitcoin history is incomplete

Owner: app + LibWallet network configuration. Evidence: static-confirmed and
prior native network-inventory checks.

`lib/services/wallet/libwallet_backend.dart:2503` filters transaction history by
address but not network. The same EVM address on several networks can therefore
mix transactions and explorer targets. It also lowercases case-sensitive Solana
addresses. Pagination stops on the first page containing any match, leaving
older matching entries unrequested by this API call.

The bundled BTC/BCH/LTC/DOGE configurations have no history provider. That means
the current backfill cannot be assumed to discover external/incoming history.
Solana-specific enrichment does not validate multi-network EVM swap labels.

Action: address + chain/network keys, chain-correct address comparison,
user-accessible pagination, and supported history providers or clear UI limits.

## Verification And Reproduction

Baseline before audit test additions: 707 passed, 13 skipped; analyzer clean.
Final full run after seven additional audit checks: 714 passed, 13 skipped,
no failures; `flutter analyze`: no issues found. Full local output is at
`/tmp/tibane-app-audit-2026-10-23.log`.
The skips include 11 opt-in live network checks and the two strict EVM adapter
checks. A green default run must not be interpreted as those features working.

Strict adapter reproduction (expected to fail twice on the current tree):

```bash
flutter test test/multichain_transfer_audit_test.dart \
  --dart-define=MULTICHAIN_STRICT_TRANSFERS=true --reporter expanded
```

Observed result: 6 passed, 2 failed. Failures are the incorrect native ETH and
ERC-20 simulation payloads. No transaction was sent.

New audit characterization coverage:

```bash
flutter test test/app_audit_signing_integration_test.dart \
  test/app_audit_browser_bridge_test.dart test/send_form_test.dart \
  test/swap_screen_test.dart test/logical_wallet_test.dart --reporter expanded
flutter analyze
```

The added characterization assertions intentionally demonstrate CURRENT broken
behavior, rather than asserting it is correct. Convert them into correct-behavior
regressions when implementing fixes. The isolated NaN widget reproduction was
replaced by a deterministic parser assertion to avoid leaving an unhandled
asynchronous exception in the default test suite.

The browser callback proof verified the actual source interpolation pattern
and executed its construction in Node's isolated VM with a harmless boolean
expression as ID. Real WebView cross-origin and navigation tests remain needed.

## Limits And Release Recommendation

Reviewed paths include imports, duplicate handling, private-key export,
backup/restore, MPC committee collection, password/device recovery, account
removal/grouping, SEND/MAX, swap, transaction history, Web3/WalletConnect,
staking and shared signing helpers. Full automated tests were exercised.

This was not an exhaustive line-by-line review of every view and dependency.
Remote fleet/backend source, deployment credentials, release build hardening,
real iOS/Android keystore recovery, cloud upload completion, WalletConnect
relay behavior and all live chain/provider combinations were not certified.
No secret-exfiltration finding should be inferred from the absence of a tested
attack. There is no justified claim here that the app is production-safe.

Prioritize A01-A09 before expanding real-fund testing. Coordinate native signing
and mnemonic capability fixes with Mark, while fixing app-level backup scope,
context binding and management-model assumptions independently.
